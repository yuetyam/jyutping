Plan: Implement input memory export and import for the macOS input method.

Status: Export implemented (2026-10-14); import implemented (2026-10-15). Both verified with a developer-installed build.

## Goal

Allow users to export the macOS input method's learned entries to one portable SQLite file at a user-selected location. The file must preserve a consistent snapshot of the stored words, romanizations, frequencies, and timestamps, and remain usable independently of the live memory database.

Allow users to import such a file back into the macOS input method, merging its entries into the live memory without losing existing entries.

The first release covers export and import in `InputMethod`. Export and import on other platforms can follow using the same versioned format.

## Current integration points

- `InputMethod/InputMemory/InputMemory.swift` exposes the live database URL and readiness API for `memory2608` in `URL.libraryDirectory.appending(path: "memory.sqlite3", directoryHint: .notDirectory)`. `InputMemoryPreparation.swift` owns its shared preparation task, migration, and `SQLITE_OPEN_READWRITE | SQLITE_OPEN_CREATE | SQLITE_OPEN_FULLMUTEX` connection.
- `InputMethod/InputMemory/MemoryLexicon.swift` defines the stored values. `latest` is Unix time in milliseconds, and `frequency` and `latest` use `Int64`. The macOS table also stores `id`, `char_count`, `letter_count`, `complexity`, `anchors`, and `spell` for internal use.
- `InputMethod/Preferences/InputMemorySettingsView.swift` contains the input-memory toggle, the Export and Import buttons, and Clear with confirmation and a simulated one-second progress display. `InputMemoryExportController.swift` and `InputMemoryImportController.swift` retain operation state across sidebar navigation and preferences dismissal. Clear currently calls the synchronous, nonthrowing `InputMemory.deleteAll()` immediately after confirmation.
- `InputMethod/Preferences/SettingsContentView.swift` routes the `.memory` sidebar selection to `InputMemorySettingsView`; these controls are no longer in `GeneralSettingsView`.
- `SettingsWindow.shared`, defined in `InputMethod/CandidateWindow.swift`, is the preferences `NSPanel` and can serve as the parent of the save sheet.
- `InputMethod/Localizable.xcstrings` contains the `InputMemorySettingsView.ExportInputMemory.*` and `InputMemorySettingsView.ImportInputMemory.*` keys, along with the toggle, Clear, and page-title strings.
- `InputMethod/InputMemory/InputMemoryExporter.swift` and `InputMemoryImporter.swift` hold the testable SQLite work; both use the `SQLiteWrapper` package.
- `Jyutping.xcodeproj/project.xcproj` already sets `ENABLE_APP_SANDBOX = YES` and `ENABLE_USER_SELECTED_FILES = readwrite` for `InputMethod`, with `InputMethod/InputMethod.entitlements` as its entitlement source. Verify the resulting signed entitlements rather than adding duplicate configuration.

Memory preparation begins when `JyutpingInputController.bufferEvents` transitions from empty to nonempty, or when export or import calls `InputMemory.waitUntilReady()`. When migration is already complete, `@MainActor InputMemory.prepare()` opens the database and ensures its table and indexes synchronously so memory is available to the first typing session, matching the prior startup behavior. If migration is still required, it starts the same retained background preparation task used by export. Readiness and connection ownership are protected by a lock; learning, suggestions, forgetting, and clearing require successful readiness. Export and import await completion and receive initialization or migration errors, including before typing has begun.

Migration uses the `Migration2608` key with completion value `2608`. Until complete, `InputMemoryMigration2026 == 2026` selects `core_memory` as the legacy source; otherwise it selects `memory`. Progress is persisted by frequency band: first `frequency > 20 AND frequency <= 100000`, then the remaining positive frequencies down to 1. Successful completion removes obsolete migration keys and attempts to remove `userlexicon.sqlite3`. Preserve this selection, resume, and frequency policy when exposing readiness.

## Export contract

Suggested filename: `memory-${formatted-date}.sqlite3`, for example `memory-20261014-153045.sqlite3`.

Use the date pattern `yyyyMMdd-HHmmss`, a fixed Gregorian calendar, `en_US_POSIX` locale, and the current local time zone. The save panel lets the user change the filename and location; ordinary overwrite confirmation handles filename collisions.

```sql
CREATE TABLE input_memory (
    word TEXT NOT NULL,
    romanization TEXT NOT NULL,
    frequency INTEGER NOT NULL,
    latest INTEGER NOT NULL,
    UNIQUE (word, romanization)
);
CREATE INDEX ix_input_memory_frequency ON input_memory (frequency);
CREATE INDEX ix_input_memory_latest ON input_memory (latest);
PRAGMA user_version = 1;
```

The unique constraint provides an implicit index for `word` and `(word, romanization)` lookups. The two explicit indexes support ordering and filtering by usage frequency or latest update time. Build them after copying rows, within the destination transaction. Indexes are an additive optimization; version-1 readers must also accept earlier exports without these explicit indexes.

Export every row from `memory2608`, preserving the four values exactly. Preserve Unicode text, tone digits, romanization spacing, and 64-bit integers. Internal IDs, derived lookup fields, legacy tables, and settings are outside the export format. Future importers can reconstruct the derived fields.

An empty memory produces a valid version-1 database containing an empty `input_memory` table. Disabling learning does not disable export of existing entries. Snapshot time describes when the committed source state was captured; it does not change any entry's `latest` value.

## Import contract

Import accepts a version-1 file: `PRAGMA user_version = 1`, an `input_memory` table containing the `word`, `romanization`, `frequency`, and `latest` columns, and a passing `PRAGMA integrity_check`. Additional columns, missing constraints, and missing explicit indexes are tolerated. Any other version, a missing table or column, an unreadable file, or a non-SQLite file is rejected as unsupported, and the live memory is left unchanged.

Each row is validated independently. Rows are skipped, not fatal, when `word` is not nonempty TEXT, `romanization` is not TEXT made only of lowercase basic Latin letters, tone digits `1`–`6`, and spaces (with at least one letter), or `frequency` and `latest` are not positive INTEGER values. Words and romanizations are otherwise preserved exactly, including Unicode, spacing, and embedded NUL characters.

Valid rows are merged into `memory2608`, with the derived fields (`char_count`, `letter_count`, `complexity`, `anchors`, `spell`) rebuilt through `MemoryLexicon`:

```sql
INSERT INTO memory2608 (word, romanization, frequency, latest, char_count, letter_count, complexity, anchors, spell)
VALUES (?, ?, ?, ?, ?, ?, ?, ?, ?)
ON CONFLICT (word, romanization) DO UPDATE SET frequency = MAX(frequency, excluded.frequency), latest = MAX(latest, excluded.latest);
```

An existing entry keeps the larger frequency and the later timestamp, so re-importing the same file, including one exported from this Mac, changes nothing. Frequencies are deliberately not summed, which would inflate counts on every repeated import. Entries absent from the file are kept. The reported count is the number of valid rows merged, whether they were inserted or updated. Disabling learning does not disable import.

## Implementation sequence

### 1. Expose memory readiness

Add a narrow asynchronous readiness API to `InputMemory` that prepares the store, awaits any migration already in progress, and reports initialization or migration failures. Concurrent callers should share the same preparation work, with readiness state synchronized explicitly.

Centralize the live database URL in `InputMemory` so preparation, export, and destination protection use the same source location. Keep the controller's existing preparation entry point compatible with the shared readiness work. Export must await readiness even when learning is disabled.

Preparation must report database-open, table/index creation, legacy-read, and migration-write errors rather than silently treating them as success. Distinguish an absent or empty legacy table from a failed query; only persist a frequency-band checkpoint after its transaction commits, and only mark migration complete and perform cleanup after all required work succeeds. Clear the in-progress state on failure and retain enough state for a later retry.

Export must not read a partially migrated table or mistake a failed database open for an empty store. Preserve the existing migration guards and normal learning behavior; polling `isMigrating` or checking the saved completion marker alone is insufficient to establish successful readiness.

### 2. Build a testable SQLite exporter

Add `InputMethod/InputMemory/InputMemoryExporter.swift`, accepting the source database URL exposed by `InputMemory` and a private output URL, and returning the exported row count. Keep save-panel presentation, localized messages, and final publication outside this component.

Run SQLite work off the main actor with connections owned by the export operation. After readiness completes, open a separate read-only source connection without `SQLITE_OPEN_CREATE` and use SQLite's backup API to create a private, consistent snapshot. A missing source must fail rather than become a new empty database. Copy in bounded steps, allowing other work between steps, and bound busy retries and total wait time so ongoing writes cannot leave export waiting indefinitely.

Stream `word`, `romanization`, `frequency`, and `latest` from the completed snapshot into a fresh export database using one destination transaction and a reusable prepared insert statement. Use bound values and 64-bit integer APIs. Row streaming keeps memory usage bounded; the private snapshot avoids sharing transaction state with the live connection.

Check SQLite return values, distinguish end-of-query from read errors, roll back failed transactions, finalize statements, and close connections before publication. Produce a standalone database that requires no WAL or journal sidecars. Validate its schema, version, row count, and `PRAGMA integrity_check` before reporting it ready.

### 3. Select the destination and publish safely

Present an asynchronous `NSSavePanel` sheet attached to `SettingsWindow.shared`, with the suggested filename and a SQLite content type supporting `.sqlite3`.

Use the existing User Selected File Read/Write configuration for `InputMethod`, and verify `com.apple.security.app-sandbox` and `com.apple.security.files.user-selected.read-write` in the resulting signed product. Keep any required security-scoped access active through publication, releasing it afterward. This export does not require a persistent bookmark.

Build and validate the export in private temporary storage before modifying the selected destination. Use a Foundation replacement workflow that supports the selected file's sandbox authorization and preserves an existing destination if publication fails. Do not assume that selecting one file grants arbitrary access to sibling files; verify staging and replacement under the actual sandbox before finalizing this implementation.

Reject destinations referring to the live source database, including symlink or file-identity aliases, and protect its SQLite sidecars. Clean up private snapshots and temporary exports on success, failure, or cancellation. Success means the validated file has been published, not merely that SQLite insertion has completed.

### 6. Implement import

`InputMethod/InputMemory/InputMemoryImporter.swift` accepts the selected file URL and the live database URL from `InputMemory`, and returns the merged row count. It keeps panel presentation and localized messages outside, matching the exporter.

1. Capture: open the selected file read-only and use SQLite's backup API, with the same bounded steps and timeout as export, to copy it into a private temporary directory. Normalize the snapshot to `journal_mode = DELETE`. Later steps never touch the selected file again, so its sandbox access is only needed during capture.
2. Validate: check the version, table, columns, and integrity of the snapshot. SQLite open, backup, and validation failures become `InputMemoryImportError.unsupportedFormat`; a backup timeout remains `SQLiteError.timedOut`.
3. Merge: open a separate read-write connection to the live store without `SQLITE_OPEN_CREATE`, so a missing store fails rather than being created, with a 5-second busy timeout. Stream snapshot rows through one reusable upsert statement inside a single `BEGIN IMMEDIATE` transaction. Cancellation is checked per row; any error or cancellation rolls back every change. Statements are finalized and connections closed before returning, and the temporary directory is always removed.

The separate connection keeps import from sharing transaction state with typing. Learning writes that collide with the brief import transaction wait for their existing 100 ms busy timeout and may be dropped, as with any other contention.

`InputMethod/Preferences/InputMemoryImportController.swift` is a `@MainActor` singleton mirroring the export controller:

```text
Select file → Await readiness → Capture snapshot → Validate → Merge → Report success
```

- An `NSOpenPanel` sheet attached to `SettingsWindow.shared` selects one `.sqlite3` file. Closing preferences cancels the sheet, and cancellation is a normal exit.
- Security-scoped access to the selected file is held for the duration of the operation.
- The SQLite work runs in a detached utility task, with cancellation forwarded.
- Errors are reported by phase: preparation failure reuses `ExportInputMemory.PreparationFailed`; `unsupportedFormat` reports `ImportInputMemory.UnsupportedFile`; a timeout, `SQLITE_BUSY`, or `SQLITE_LOCKED` during merge reports `ImportInputMemory.Busy`; other merge failures report `ImportInputMemory.ImportFailed`, which states that no entries were changed.

`InputMemorySettingsView` wires the Import button to the controller, shows `ImportInputMemory.Progress` with the indeterminate indicator while active, and presents a separate alert titled with `ImportInputMemory.ButtonTitle`, dismissed with the shared `ExportInputMemory.Dismiss` string. The alert is attached to the Import row so it does not conflict with the export alert on macOS 13. Export, import, and Clear exclude each other: the view disables all three buttons and guards the Clear confirmation while any transfer is active, and each controller refuses to start while the other is running.

New localized keys: `ImportInputMemory.Busy`, `.ImportFailed`, `.Progress`, `.Success %lld`, and `.UnsupportedFile`, translated for `en*`, `fr`, `ja`, and `yue`, with every `zh-*` locale matching `yue`.

## Completion criteria

- Export produces one portable version-1 `.sqlite3` file at the selected location.
- Import accepts version-1 exports, merges valid entries atomically with the larger frequency and later timestamp, skips invalid rows, and rejects unsupported files without changing memory.
- The file contains an exact, consistent snapshot of all four exported columns and works independently of the source database.
- Preparation, migration, export, and import failures are distinguishable from a valid empty memory.
- Typing remains responsive, repeated operations are controlled, and temporary resources are cleaned up.
- Existing destination files remain intact on failure, the live memory database cannot be overwritten by export, and a failed or cancelled import leaves it unchanged.
- File selection, publication, and import reading work with the signed application's sandbox permissions.
- Automated checks and installed runtime validation substantiate these behaviors.
